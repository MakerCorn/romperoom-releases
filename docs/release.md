# Releasing

How a Romperoom release is built, checked and published. The source repository is private;
players download from a separate, public, **releases-only** repository that holds no source
([decisions.md](decisions.md#14-private-source-public-releases)). Every build is a draft until
a person publishes it.

## What a release contains

electron-builder 26 (`apps/desktop/electron-builder.yml`, the version pinned in
`apps/desktop/package.json`) builds, per release:

| File                                    | What it is                                                         |
| --------------------------------------- | ------------------------------------------------------------------ |
| `Romperoom-X.Y.Z-mac-arm64.dmg`         | macOS disk image, Apple silicon, macOS 12 or later                 |
| `Romperoom-X.Y.Z-mac-arm64.zip`         | The same app as a zip archive                                      |
| `Romperoom-X.Y.Z-win-x64.exe`           | Windows installer (NSIS), per user, no administrator rights        |
| `Romperoom-X.Y.Z-win-x64.zip`           | The same app as a zip archive, no installer                        |
| `Romperoom-X.Y.Z-linux-amd64.deb`       | Linux x64 package (Ubuntu, Debian); installs the sandbox helper    |
| `Romperoom-X.Y.Z-linux-x86_64.AppImage` | The same app as an AppImage, for other distributions               |
| `SHA256SUMS.txt`                        | SHA-256 of every file above, for `shasum -a 256 -c`                |
| `SHA256SUMS.txt.sig`                    | Ed25519 signature of `SHA256SUMS.txt`, for the in-app updater      |

- App id `app.romperoom.desktop`, product name `Romperoom`. The data folder is named after the
  product name ([configuration.md](configuration.md#data-folder)), so renaming the product would
  move every player's catalogue: do not.
- The Windows installer asks where to install (default `%LOCALAPPDATA%\Programs\Romperoom`),
  creates Start menu and desktop shortcuts, and its uninstaller keeps the data folder.
- Each app carries `THIRD_PARTY_NOTICES.txt` (generated by `scripts/third-party-notices.mjs`
  from the packages it ships; a package with an unknown or missing licence fails the build) and
  Electron's and Chromium's own licence files.
- The icons are generated (`npm run icons -w @romperoom/desktop`, `scripts/make-icons.mjs`);
  `test/icons.test.ts` fails when the committed files are not the generator's pixels.

## Versioning

- One version for the product, in `package.json` and `apps/desktop/package.json` (they must
  agree; the release workflow fails otherwise). The workspace packages stay `0.0.0`, private and
  `UNLICENSED`: nothing is published to npm (`apps/desktop/test/manifests.test.ts`).
- Semantic versioning. `0.x` is the beta: anything may change between minors, and breaking
  changes are called out in the release notes.
- The tag is `v` plus the version (`v0.1.0`). The release notes are the conventional commits
  since the previous `v*` tag (`releases-repo-template/scripts/make-release-notes.mjs`): `feat`,
  `fix`, `perf` and breaking changes only, without commit hashes, pull request numbers or links,
  which would point into the private repository.

### Required release-note lines

The notes come from commit subjects, which cannot carry a caveat. Until it no longer applies,
every release from 0.11.0 on must say, in its notes:

> Look up on ScreenScraper is built, but this release can't use it yet: Romperoom first has to
> be registered with ScreenScraper. Until then the button says "This copy of Romperoom can't use
> ScreenScraper yet."

Add it to the draft's notes before publishing (step 5 below), and keep it in the squash-merge
body of the pull request that brings the feature, so the history carries it too. Remove it here
in the change that ships Romperoom's registration.

## Building locally

Run at the repository root, after `npm ci` and `node node_modules/electron/install.js`
([development.md](development.md#electron-binary)). Packaging needs the built app:

```sh
npm run build
npm run package:dir -w @romperoom/desktop     # unpacked app only (fast)
npm run verify:package -w @romperoom/desktop  # fuses, asar integrity, contents, notices
npm run e2e:packaged -w @romperoom/desktop    # --self-check, refused switches, a real launch
npm run package -w @romperoom/desktop         # installers, archives and SHA256SUMS.txt
```

- Output goes to `apps/desktop/release/` (ignored by git). macOS builds macOS artifacts, Windows
  builds Windows artifacts and Linux builds Linux artifacts; there is no cross-building.
- `package` takes `--arm64` or `--x64` (default: this machine's). `verify:package` takes
  `--arch` and an optional app path; `e2e:packaged` reads `PACKAGED_APP_PATH`
  ([configuration.md](configuration.md#packaging-and-release-variables)).
- Without signing variables the build is unsigned, even on a Mac with a Developer ID in its
  keychain (identity discovery is switched off). See
  [Unsigned and signed builds](#unsigned-and-signed-builds).
- A dmg build downloads electron-builder's dmg tooling on first use; everything else comes from
  `node_modules` and the Electron cache.

## Before each release

First, re-record the game database listing, on the maintainer's own network:

```sh
npm run record:libretro
git diff packages/profiles/data/libretro.json
```

It asks `api.github.com` (four unauthenticated requests) for libretro-database's current
commit and its `metadat/no-intro`, `metadat/redump` and `dat` listings, and rewrites the shipped
listing, keeping the console mapping. Review the diff before committing it: a new commit, files
added or removed, and any `mapping problems` the script prints (a mapped file no longer in the
listing shows "not available at this version" until the mapping is fixed). A diff of
`recordedAt` alone means nothing changed upstream; it need not be committed. The listing is
metadata only (names, sizes, git SHAs), never a DAT.

Then re-record the cover art repository list the same way:

```sh
npm run record:thumbnails
git diff packages/profiles/data/thumbnails.json
```

It asks `api.github.com` (one unauthenticated request per 100 repositories: two today) for the
libretro-thumbnails organisation's repositories and their default branches, and rewrites
`thumbnails.json`. Review the diff: a repository added or removed, or one whose branch moved
between `master` and `main` (cover art asks only for the recorded branch, so a moved one shows
"not available" until this list is updated). Then run the
[live cover art run](testing.md#live-cover-art-run) if anything under the art code changed.

Then two checks for identify, run on the packaged app
(`npm run package:dir -w @romperoom/desktop`) and recorded with the release:

- **No game database ships.** Users import their own DATs or have Romperoom download them when they
  ask; the app bundles none (see [user guide](user-guide.md#identify-your-games)). List the archive,
  and search the unpacked files and the rest of the resources folder; expect no output from either:

  ```sh
  RES=apps/desktop/release/mac-arm64/Romperoom.app/Contents/Resources
  npx asar list "$RES/app.asar" | grep -i '\.dat$'
  find "$RES" -iname '*.dat'   # app.asar.unpacked/ and every extra resource
  ```

  On Windows `RES` is `apps/desktop/release/win-unpacked/resources`.

- **Identify works in the packaged app.** `npm run e2e:packaged -w @romperoom/desktop` (CI and
  the release workflow run it on every build) requires `--self-check`'s `identify` check to
  pass. That check imports a one-game DAT written for the bundled `self-check.bin`, scans a
  temporary library holding that file, and identifies it by hash: the shipped DAT parser, the
  unpacked hash worker and the matcher, inside the packaged app
  ([configuration.md](configuration.md#command-line-switches)). By hand, on the macOS build:

  ```sh
  apps/desktop/release/mac-arm64/Romperoom.app/Contents/MacOS/Romperoom --self-check \
    | grep -o '"name":"identify","status":"[a-z]*"'
  ```

  Expect `"name":"identify","status":"pass"`. If neither was run on this build, record it as not
  run; never as passed.

## Cutting a release, step by step

1. **Green main.** Every CI job is green for the commit to release, on macOS, Windows and
   Linux, including `package`. Review the non-blocking `npm audit` findings in the CI summary.
2. **Bump the version** in `package.json` and `apps/desktop/package.json`, run `npm install`
   so the lockfile agrees, and merge that as `chore(release): X.Y.Z` through a pull request.
3. **Tag the merged commit** and push the tag:
   `git tag -a vX.Y.Z -m "Romperoom X.Y.Z"` then `git push origin vX.Y.Z`.
4. **Watch the release workflow** (Actions, `release`). The tag push rebuilds and re-checks
   everything and drafts a release named `Romperoom X.Y.Z` in the private repository.
5. **Check the draft by hand** before anyone else sees it:
   - download each file and run `shasum -a 256 -c SHA256SUMS.txt` (Windows: `Get-FileHash`),
     and check the signature from a checkout of the tag:
     `node apps/desktop/scripts/update-signature.mjs verify <folder>` prints `OK`;
   - install on a clean macOS account (Apple silicon) and on a Windows PC, open each the
     unsigned way ([the public README](../README.md)), run the wizard on
     a test library, and confirm the wall loads cover art;
   - drag a `.html` file and a ROM onto the wizard and the wall: the window must stay on the app
     ([security.md](security.md#gaps));
   - read the release notes: user-facing, nothing private, and carrying every
     [required line](#required-release-note-lines) (edit the draft's notes to add one; an
     edited draft keeps its notes);
   - [Before each release](#before-each-release) was run on this build, or is recorded as not
     run.
6. **Publish publicly** ([below](#publishing-to-the-public-repository)): **Run workflow** with
   the tag and **publish** ticked. The draft is finished, so that run builds nothing and
   publishes exactly the files you checked. The private release must still be a draft: the
   workflow never touches a published release, so a run for a published tag stops at once.
7. **Publish the draft** in the private repository.

A dry run: **Run workflow** on a branch, with the tag input empty, builds and checks every
platform and creates and uploads nothing: no release, no assets, no artifacts (traces of a
failed run excepted). Its installers are not kept; to try one, build it locally or tag.

## The release workflow

`.github/workflows/release.yml`, on a pushed `v*` tag or **Run workflow**. The files move
between jobs as assets of the private draft release, never as Actions artifacts: artifact
storage has an account quota, and a full quota stopped the 0.7.0 release at its upload step.

1. **prepare**. Decides what the run releases: the **tag** input if given, else the tag the run
   is on, else nothing (a dry run). A tag must be exactly `vX.Y.Z` and exist in this repository,
   and its two `package.json` versions must name it. Then it creates the draft release for the
   tag, empty, or reuses the existing draft; it stops if the release is already published, the
   tag has more than one release, or the releases cannot be listed. Creating the draft once,
   before the builds, keeps the three builds from racing to create it. On a run with
   **publish** ticked it checks whether the draft is already finished: notes set, no per-build
   sums left, every build present, every file listed in a `SHA256SUMS.txt` that verifies, and a
   `SHA256SUMS.txt.sig` that verifies against the app's keys (a draft without one is built and
   signed again while the tag's app trusts a key, unless the run allows unsigned).
   If so the run is **publish only**: `build` and `release` are skipped and the checked files
   are published as they are. A draft that is missing or unfinished is built first. A draft
   that looks finished but holds unlisted files or fails its sums stops the run.
2. **build** (macOS arm64, Windows x64 and Linux x64, in parallel), from the tag's code.
   Checks that the tag names the version, then runs lint, type-check and the coverage gate
   again, `npm run build`, `package` with the signing secrets if any, `verify:package`,
   `e2e:packaged` and `checksums.mjs --verify`. On a release run it uploads exactly the files
   its `SHA256SUMS.<build>.txt` lists, and that file, to the draft, replacing same-named files
   of an earlier run. Before every delete and upload it checks the release is still a draft,
   and stops if it is not. On a dry run it uploads nothing. Traces and screenshots of a failed
   packaged-app check are kept as a run artifact for 3 days, when the quota allows; a failed
   trace upload does not fail the job.
3. **release** (needs every build; not on a dry run). Downloads the draft's files, requires
   exactly one sums file per build (`mac-arm64`, `win-x64`, `linux-x64`: a missing platform
   fails the run), checks every build's sums against the files and merges them into one
   `SHA256SUMS.txt` (`checksums.mjs --merge`), and fails on any file on the draft that no build
   listed. It writes the release notes, uploads `SHA256SUMS.txt`, removes an earlier run's
   `SHA256SUMS.txt.sig`, sets the notes on a draft it created (an edited draft keeps its notes),
   and removes the per-build sums files, leaving the installers and `SHA256SUMS.txt`. It checks
   the release is still a draft before each change, and stops without changing it once someone
   has published it.
4. **sign** (after `release`), on the self-hosted Linux runner (`LINUX_RUNNER_LABELS`, never the
   Mac) in the `release-signing` environment ([below](#signed-checksums)): downloads `SHA256SUMS.txt` from the draft, requires it to be
   exactly the list `release` checked (its SHA-256), signs it (`update-signature.mjs sign`, the
   only step that sees the key), runs the positive and negative controls without the key,
   attaches `SHA256SUMS.txt.sig` to the draft and verifies what the draft then holds. No key
   while the app trusts one fails the run.
5. **publish-public**. Only on **Run workflow** with a tag and **publish** ticked (after
   `sign`, or straight after `prepare` on a publish-only run): it downloads the private
   draft's files and notes, checks the sums and the signature again, syncs the documentation and
   drafts the release in the public repository, pushing the docs only after the draft exists.
   Otherwise it writes the manual steps to the run summary
   ([below](#publishing-to-the-public-repository)).

**Releasing an existing tag from `main`.** A run builds the tag's code with the workflow of the
ref it runs on. So when a tag's own workflow is broken (v0.7.0's used Actions artifacts), run
the current one from `main` against the tag, without moving it. The `sign` job cannot receive
the key on a run from a branch (the environment admits tag refs only). So a run from a branch
for a tag whose app trusts an update key stops in `prepare`, before any build, and says what to
do instead; with **allow_unsigned** ticked it builds, skips `sign` and leaves the draft unsigned
(the app will not install it). A tag older than signed checksums has no `update-signature.mjs`
and trusts no key: a branch run builds it, and needs **allow_unsigned** too, or its `sign` job
is refused and nothing is published (a finished draft of it publishes without). What works:

```sh
# The tag's own run failed only at sign (or later): in its run page, Re-run failed jobs.
# It runs on the tag ref, keeps the checked list, and signs it. Cheapest; nothing is rebuilt.
# The tag's own workflow works: run on the tag ref, which can sign.
gh workflow run release.yml --ref vX.Y.Z -f tag=vX.Y.Z
# The tag's own workflow is broken and no key is available: build unsigned from main.
gh workflow run release.yml --ref main -f tag=vX.Y.Z -f allow_unsigned=true
# A finished (checked) draft, signed or not: publish exactly its files, from any ref.
gh workflow run release.yml --ref main -f tag=vX.Y.Z -f publish=true
```

How each run goes:

| Run | prepare | build, release | sign | publish-public |
| --- | --- | --- | --- | --- |
| push of tag `vX` | makes the draft | run | signs (tag ref, the Linux runner) | summary only |
| Re-run failed jobs of that run | (kept) | (kept) | signs again (tag ref) | as asked |
| `--ref vX -f tag=vX -f publish=true`, draft unfinished | building | run | signs (tag ref) | publishes |
| `--ref main -f tag=vX -f publish=true`, draft finished and signed | publish only | skipped | skipped | publishes (verifies the `.sig`) |
| `--ref main -f tag=vX`, draft unfinished, app trusts a key | **stops here** (before any build) | skipped | skipped | skipped |
| the same with `-f allow_unsigned=true` | building | run | skipped | publishes unsigned if asked |
| `--ref main -f tag=<tag before signing>` | building | run | refused (branch ref); skipped with allow_unsigned | only with allow_unsigned: publishes unsigned if asked |

The tag input is checked before use (exactly `vX.Y.Z`, an existing tag) and reaches the shell
only as an environment variable. A run for the tag input queues behind a run for a push of the
same tag rather than racing it. The workflow runs the tag's own copies of
`.github/actions/ensure-gh`, `apps/desktop/scripts/checksums.mjs`,
`releases-repo-template/scripts/make-release-notes.mjs` and `scripts/publish-docs.mjs`, so an
older tag works only if it has them with the same interfaces (v0.7.0 does).

**Re-running.** Before the draft is checked, a re-run of the whole workflow refreshes the
draft's files. If the release job fails after it removed the per-build sums files, re-run all
jobs, not only the failed one: it needs every build's sums on the draft. Once the draft has
been checked, never re-run a build: start a publish run, which builds nothing for a finished
draft.

**Recovering a failed sign job.** Fix the cause (the runner offline, the secret missing, a
payment or spending limit that kept a job from starting), then open the tag's run and **Re-run
failed jobs**: `sign` runs again on the tag ref with the list `release` checked, and nothing is
rebuilt. A fix to the workflow itself needs a new tag (a patch version): a tag's run always uses
the workflow at that tag, so re-running it, or running on that tag, repeats the old workflow.

Every third-party action in `release.yml` and `ci.yml` is pinned to a full commit SHA with the
release it names as a comment (`uses: actions/checkout@<sha> # v4.4.0`), so a moved tag cannot
change what a release runs. `apps/desktop/test/workflows.test.ts` fails on any `uses:` that is
not pinned that way (local `./` actions excepted). To update one, look up the tag's commit
(`gh api repos/<owner>/<repo>/git/ref/tags/<tag>`, and for an annotated tag follow its
`object.url` to the commit) and change the SHA and the comment together.

Permissions are `contents: read` by default. `prepare`, `build` and `release` have
`contents: write` on this repository, for the draft release only. `publish-public` has it too,
only because GitHub shows draft releases to tokens that can push; it uses its own token for
nothing but downloading the private draft, and writes to the public repository only with
`PUBLIC_RELEASES_TOKEN`. Runs for the same release queue rather than cancel. CI's `package` job
(`ci.yml`) runs the same `package:dir`, `verify:package` and `e2e:packaged` on every push and
pull request, so a packaging regression shows up before a release.

The build jobs hold `contents: write` for the whole job (permissions cannot be per step), and
use the token only in their upload step. On a persistent self-hosted runner, code that runs
earlier in the job (a dependency's install script) could in principle outlive its step and
read that step's environment. An ephemeral runner for release builds would close that.

## Publishing to the public repository

The public repository, `MakerCorn/romperoom-releases` (the `PUBLIC_RELEASES_REPO` variable),
was created from `releases-repo-template/` (a README with the download table, install help and
checksum instructions; `SECURITY.md`). It holds no source.

**Once:**

1. Create the repository, public, with the contents of `releases-repo-template/` as its first
   commit (the `scripts/` folder can stay in the source repository). Replace the README's
   `OWNER/REPO` placeholders. Then run the documentation sync once (the by-hand steps below):
   until it runs, the README's Documentation links point to `../docs/` and are broken.
2. Check its visibility anonymously:
   `curl -s -o /dev/null -w '%{http_code}' https://api.github.com/repos/OWNER/REPO` must print
   200 for the public repository and 404 for `MakerCorn/romperoom` (a known public repository
   is the control). A repository created as private once came out public, so check both.
3. Turn on private vulnerability reporting (Settings, Code security) and issues.
4. Optional, for the automated path: in the private repository, set the variable
   `PUBLIC_RELEASES_REPO` (`OWNER/REPO`) and the secret `PUBLIC_RELEASES_TOKEN`: a fine-grained
   token with **Contents: read and write** on that one repository only, stored in the cloud
   secret store and copied into the repository secret, never into a file or a chat.

**Each release, automated:** once the tag push has built the private draft and you have checked
it, **Run workflow** on the tag `vX.Y.Z` (on `main` with the tag input `vX.Y.Z` works too while
the draft is finished and signed, as nothing is built or signed then) with
**publish** ticked, while the private release is still a draft. The draft is finished, so the
run builds nothing. The job downloads the private draft's files and notes, checks the sums
and the signature again (a draft without `SHA256SUMS.txt.sig` stops it while the app trusts a
key, unless the run allows unsigned), then syncs the documentation: it clones the public
repository's `main` with the token and runs `scripts/publish-docs.mjs` over the clone. If the sync finds a problem, the job stops
there and nothing reaches the public repository. Then it creates a
**draft** in the public repository with the same files and notes; it stops if that repository
already has the release. Only once the draft exists does it commit any documentation change as
`docs: sync documentation for vX.Y.Z` and push it to `main`, so a failed draft leaves the public
docs untouched. Then update the README's download table and version, and publish the draft.

If the push fails after the draft exists (`main` moved between the clone and the push, or a new
protection rule), do not re-run the workflow with **Re-run all jobs**; use only **Re-run failed
jobs**, which re-runs the publish job alone and stops at the existing public draft. Then push
the documentation by hand (below), from a checkout of the same tag; the draft is unaffected.

**Each release, by hand:** sync the documentation from a checkout of the tag, review the
change, then commit and push it:

```sh
git clone https://github.com/OWNER/REPO.git /tmp/rr-public
node scripts/publish-docs.mjs --src . --dest /tmp/rr-public
git -C /tmp/rr-public diff --stat
git -C /tmp/rr-public add -A -- docs README.md
git -C /tmp/rr-public commit -m "docs: sync documentation for vX.Y.Z"
git -C /tmp/rr-public push origin main
```

Then download the private draft's files (`gh release download vX.Y.Z --dir dist`), check them
(`cd dist && shasum -a 256 --check --strict SHA256SUMS.txt`, then, from the checkout,
`node apps/desktop/scripts/update-signature.mjs verify dist`), create the release `vX.Y.Z` in the
public repository, attach every file in `dist/`, `SHA256SUMS.txt.sig` included (without it the
app cannot install the release), paste the private draft's notes, update the README table,
publish.

**What the documentation sync does** (`scripts/publish-docs.mjs`, the same on both paths):

- It copies every `docs/*.md` except `docs/superpowers/**` (the design specs and plans stay private)
  into the public `docs/`, with every picture and file they link, inline (`![alt](path)`) or
  reference-style (`![alt][label]` and `[label]: path`). Containment is checked on the real path,
  not the link's text: a file is refused if it or any folder on its way is a symbolic link, or if
  its real path (in the disk's own letter case) is outside `docs/` or inside `docs/superpowers`. A
  refused file stops the run before anything is written. Public `docs/` files the source no longer
  has are removed. Nothing outside `docs/` is touched except one section of the README;
  `SECURITY.md` and the README's download table never change.
- Links into private material (`docs/superpowers/`, `packages/`, `apps/`, `.github/`, `scripts/` and
  `ci/`) become their visible text, a path as inline code. A different letter case of those paths
  (`SuperPowers/`) is not converted: the check below fails it. A link to a heading in a private
  document names the section instead ("design spec (Live verification section)"). Links to
  `releases-repo-template/README.md` and `SECURITY.md` point to the public repository's own
  `README.md` and `SECURITY.md`; links to the source's root `README.md` already land on the public
  one. Links between published documents, anchors included, stay as they are.
- The README's **Documentation** section, between its `docs-index` markers, is replaced by the
  block between the same markers in `releases-repo-template/README.md`: edit the table there,
  with links relative to the template (`../docs/user-guide.md`, so this repository's docs tests
  check them); they are published relative to the README. On a README without markers, the
  first run converts its existing Documentation section.
- Then it checks the public tree and exits non-zero, listing every failure: each local link,
  anchor (GitHub's heading slugs, one hyphen per space) and picture in `docs/` and the README
  resolves; no link is left into private material, in any letter case; no raw HTML link or
  picture (`<img src>`, `<a href>`) has a local target, since the sync neither rewrites nor
  resolves HTML: use Markdown; nothing under `docs/` is a symbolic link; the README section links
  every published document; PNGs carry no text metadata (`tEXt`, `zTXt`, `iTXt`, `eXIf`) and
  other picture formats are refused (their metadata cannot be checked); and every other
  published file, whatever its type, passes a privacy scan. The scan's patterns
  (`PRIVACY_PATTERNS` in `scripts/lib/publish-docs.mjs`; written out only there, since this page
  is published and would fail them) cover the three private IPv4 ranges, home-folder paths on
  macOS, Linux and Windows, macOS volume paths, email addresses, ssh key use, every GitHub token
  prefix, AWS access keys, private key blocks and the name of the private repository. They catch
  the common shapes, not every secret. Known mentions are allowed only by their exact text in
  their own file (`PRIVACY_ALLOW`): the runner registration path and the runner's Docker volume
  in [ci-runners.md](ci-runners.md), and the visibility check above.
- A source problem (a refused file, no README block in the template) means nothing is written.
- `--check --dest <clone>` runs the checks without writing; with `--src .` it also lists what a
  sync would change.

## Unsigned and signed builds

The beta ships **unsigned** ([decisions.md](decisions.md#16-the-beta-ships-unsigned)). macOS
Gatekeeper and Windows SmartScreen warn on first open; the public README explains how to open the
app anyway and why it is unsigned. The packaging is ready for signing; only credentials are
missing.

| Mode     | When                                        | What happens                                                                                                                             |
| -------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Unsigned | No `CSC_LINK` (Windows: `WIN_CSC_LINK`) set | `CSC_IDENTITY_AUTO_DISCOVERY=false`, and on macOS `mac.identity=null`: the app gets only the ad-hoc signature Apple silicon requires.    |
| Signed   | The certificate variable is set             | `forceCodeSigning`: the build fails rather than ship unsigned. macOS signs with the hardened runtime and `build/entitlements.mac.plist`. |

- **Notarization** runs when a macOS build is signed and the Apple variables are set
  (electron-builder's `@electron/notarize` integration). Apple's recommended form is an App Store
  Connect API key (`APPLE_API_KEY`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER`); the workflow wires
  the Apple ID form, which needs no key file on the runner.
- The fuses are flipped in `afterPack`, **before** signing, so the signature covers them.
- The entitlements are one: `com.apple.security.cs.allow-jit`, which V8 needs under the hardened
  runtime. Electron's default entitlements file also grants the camera, microphone, Bluetooth,
  USB, printing and location; Romperoom uses none of them, so it does not take them.

## Secrets and variables

All optional except `UPDATE_SIGNING_KEY` while the app trusts an update key. Unset signing
certificates mean an unsigned build. Secrets live in the cloud secret store and are copied into
the repository's Actions secrets, except the two update keys, which exist only in the
`release-signing` environment (kind `env`, [below](#signed-checksums)); the workflow never
prints them.

| Name                          | Kind     | Used by         | What it is                                                    |
| ----------------------------- | -------- | --------------- | ------------------------------------------------------------- |
| `CSC_LINK`                    | secret   | build (macOS)   | Developer ID Application certificate, base64 `.p12`           |
| `CSC_KEY_PASSWORD`            | secret   | build (macOS)   | Its password                                                  |
| `APPLE_ID`                    | secret   | build (macOS)   | Apple ID for notarization                                     |
| `APPLE_APP_SPECIFIC_PASSWORD` | secret   | build (macOS)   | An app-specific password for that Apple ID                    |
| `APPLE_TEAM_ID`               | secret   | build (macOS)   | The Developer team id                                         |
| `WIN_CSC_LINK`                | secret   | build (Windows) | Code-signing certificate, base64 `.pfx`                       |
| `WIN_CSC_KEY_PASSWORD`        | secret   | build (Windows) | Its password                                                  |
| `PUBLIC_RELEASES_TOKEN`       | secret   | publish-public  | Fine-grained token, Contents read and write, public repo only |
| `PUBLIC_RELEASES_REPO`        | variable | publish-public  | `OWNER/REPO` of the public releases repository                |
| `UPDATE_SIGNING_KEY`          | env      | sign            | Ed25519 key (PKCS#8 PEM) that signs `SHA256SUMS.txt`          |
| `UPDATE_SIGNING_KEY_NEXT`     | env      | sign            | Only during a rotation: the next key (a second `.sig` line)   |

The names are electron-builder's own (its `macOptions` notarize documentation and
`windowsSignToolManager`), so the same variables sign a local build.

## Rolling back

- **A draft is wrong:** delete it (and the tag, `git push origin :refs/tags/vX.Y.Z`), fix, and
  tag again. Re-running the workflow on a tag refreshes a draft's files.
- **A published release is bad:** in the public repository, edit the release to say so and mark
  the previous good release as **latest**, or delete the bad release. Update the README table.
  Do not reuse the version: ship the fix as the next patch version (`vX.Y.Z+1`), because players
  and checksum files already know the bad one.
- The workflow never edits a published release, in either repository.
- The catalogue is migrated forward only. An older build refuses a catalogue a newer one has
  migrated ("catalog was created by a newer Romperoom", `packages/engine/src/catalog/db.ts`)
  rather than damage it. So if a bad release migrated the catalogue, a player who goes back must
  also move the data folder aside; say so in the notes of any release that migrates it.

## What packaging guarantees

Each of these is checked on every CI run (`package` job) and every release build, and each check
was shown to fail on a broken build (mutation evidence in
[security.md](security.md#packaging-checklist)):

- **Fuses** ([decisions.md](decisions.md#17-electron-fuses)): set by `scripts/after-pack.mjs` with
  `@electron/fuses` from `src/main/fuse-policy.json`, read back from the binary by
  `verify:package`, and read again from inside the running app by `--self-check`.
- **asar integrity:** the hash electron-builder records (macOS `Info.plist`, Windows the
  executable's resources) equals the hash of the `app.asar` header that ships.
- **Contents:** `app.asar` holds `out/` and the production dependencies only; no source maps,
  TypeScript, tests, the smoke chunk or other platforms' native binaries. The unpacked files are
  exactly the hash worker and its dependencies (yauzl and pend), the picture worker with the
  engine's image folder and jpeg-js, and this platform's SQLite binary.
- **The packaged app works:** `--self-check`
  ([configuration.md](configuration.md#command-line-switches)) opens a fresh catalogue with the
  shipped SQLite, hashes a bundled file through the worker pool, identifies that file against a
  DAT written for it, converts an embedded JPEG to PNG through the unpacked picture worker, serves
  the page through `app://`
  from inside `app.asar`, and confirms the fuses and that DevTools and reload are off.
  `e2e:packaged` then launches the app for real with every development seam and both
  fuse-guarded variables set, and checks the catalogue is created, the app does not exit on the
  smoke timer and it logs no startup failure.
- **No remote control:** the packaged app exits with code 2 on a debugging, sandbox, proxy,
  resolver or profile switch, before any port opens; `e2e:packaged` connects to the debugging
  port the whole time and requires that nothing ever answers
  ([security.md](security.md#launch-switches)).

## Signed checksums

Settings › Updates installs a new version only from a release whose `SHA256SUMS.txt` carries an
Ed25519 signature by a key the app trusts
([decision 68](decisions.md#68-the-app-updates-itself-from-signed-checksums-without-code-signing),
[security.md](security.md#main-process-requests)).
Builds stay unsigned; this signs the list.

- **What is signed:** the exact bytes of `SHA256SUMS.txt` as published. `SHA256SUMS.txt.sig` is
  one line, the 64-byte signature in base64, or two lines during a rotation (one per signing
  key). The app accepts the file when every line is a canonical signature (no blank line, no
  third line, no CRLF) and at least one line verifies under a key it trusts; a line by a key it
  does not trust is the other key's, for copies that trust that one. The app looks its own file
  up by name in the signed list, and the name carries the version, so the signature binds the
  version too.
- **Where:** the `sign` job, after `release`, signs the merged list
  (`apps/desktop/scripts/update-signature.mjs sign`) with `UPDATE_SIGNING_KEY` and, during a
  rotation, `UPDATE_SIGNING_KEY_NEXT`. Only that step sees a key. Before anything is signed or
  verified, the script checks the list is one the app reads (at most 64 KiB, the exact line
  format, no name twice: the same rules as the app, pinned by an agreement test). The next step runs the positive
  control (`verify`, and `tamper-check` requires every line to verify on its own against
  `apps/desktop/src/main/updates/trusted-keys.json`) and the negative controls (a list changed
  by one byte and a signature by a fresh key must both be refused), with the public keys only. A
  secret whose key the app does not trust fails the release before any player gets it. The
  publish-only check and the public copy verify the `.sig` again, and the public release
  carries it.
- **Without the secret** the release fails while the app trusts a key: an unsigned release
  would leave every player unable to update from the app. **Run workflow** with
  `allow_unsigned` ticked releases it unsigned anyway (a warning in the run); the app then finds
  it, says "This release can't be installed from here." and offers the release page. Use it only
  when no signing key is available. On a tag ref the `sign` job still runs and lets the missing
  key through; on a branch ref it is skipped. It does not rescue a failed sign job: re-run that
  job on the tag's own run (the table [above](#the-release-workflow)).
- **An older tag** has no `update-signature.mjs`, so it cannot be signed: re-release from a tag
  that has the script (a new patch version) to make in-app-installable files
  ([above](#the-release-workflow)).

**The release-signing environment.** The update keys exist only as secrets of the GitHub
environment `release-signing`, whose deployment policy admits tag refs matching `v*` only; the
`sign` job is the only job that names it. What that protects: a run started from a branch (Run
workflow on `main` or any other branch) never receives the key, and pull requests never run
this workflow. The job runs on the self-hosted Linux runner, because GitHub-hosted runners are
not available on this account, and never on the Mac. What it does not protect: that runner is
shared with pull-request CI, so anything that could run code on it before a `v*` tag job could
capture the key from the sign step's environment. Mitigations: `.npmrc` sets
`ignore-scripts=true` (no dependency's install script runs), the job installs no dependencies,
and the sign step runs Node by its absolute path under `env -i` with only the keys and
`ALLOW_UNSIGNED` (no `NODE_OPTIONS`, `PATH`, `LD_PRELOAD` or `HOME` reach it). A runner used for
signing only is the stronger fix. Nor does it protect against anyone who can push a `v*` tag:
they can run a workflow from that tagged commit, a changed `release.yml` included, and that run
receives the key. Today the repository is private with a
single owner. GitHub rulesets and tag protection, which would limit who may push `v*` tags, are
not available on this plan.

**The keys trusted today.** `trusted-keys.json` holds at most two public keys:

1. `ci-2026-10`, the signing key: made on 2026-10-12 in memory and stored straight into the
   environment's `UPDATE_SIGNING_KEY`. It was never written to a file, and GitHub secrets cannot
   be read back, so no copy of it exists: overwriting or deleting that secret loses it.
2. A **cold backup key**, made by the owner on their own machine and never stored in GitHub, so
   that losing the signing key costs one secret change rather than a manual install by every
   player. Until its line is added, the signing key is the only one.

**Making the cold backup key (owner, once).** On your own machine, in a checkout of the source
repository; the private key never goes into chat, the repository, an issue or a log. Write it to
a folder no sync or backup reads (`KEYDIR` below): a file in your home folder, Documents or Desktop
can be copied by iCloud Drive or Time Machine before you delete it, and deleting a file on an SSD
is not a secure erase. A RAM disk is safest (on macOS, `hdiutil attach -nomount ram://8192` and
`diskutil erasevolume`; it is gone at the next restart), or a folder you have excluded from both:

```sh
node apps/desktop/scripts/updater-keygen.mjs \
  "$KEYDIR/romperoom-update-backup-key.pem" --id cold-2026-10
```

It writes the private key to a new, owner-only (0600) file (never replacing an existing one, and
removing a half-written one) and prints the public key line. Add that line to `"keys"` in
`apps/desktop/src/main/updates/trusted-keys.json`, its value to the allowlist in `.gitleaks.toml`
(which otherwise reads a public key as a leaked secret) and to `apps/desktop/test/release-keys.ts`,
and release. Do not store this key as a secret. Put the `.pem` file in your password manager (or
the cloud secret store), check that the copy opens, then delete the plaintext file (eject the RAM
disk, or `rm` the file where you wrote it). The script also prints the `gh secret set … --env
release-signing` commands (POSIX shell, PowerShell, cmd) for the day a key is to sign.

**Rotation.** The planned way is to promote the backup:

1. Store the cold backup key as the environment's `UPDATE_SIGNING_KEY` (the commands the script
   printed, from the password manager's copy; delete the plaintext file again), and in the same
   release replace the retired key's line in `trusted-keys.json` (and `release-keys.ts`) with a
   new cold backup key made as above; in `.gitleaks.toml` and `release-keys.ts` the retired
   public key moves to the RETIRED list (gitleaks reads the whole history, which keeps it). Every copy that trusts the
   backup verifies the new signatures at once, so no player is left behind.
2. To switch to a key no released copy trusts yet (say the cold backup's only copy was lost, so
   no trusted key can be promoted when the release key is to be retired): add it in place of the key that is not signing, then sign with both, the old key
   as `UPDATE_SIGNING_KEY` and the new one as `UPDATE_SIGNING_KEY_NEXT`, until the new key has
   been trusted by the app for at least one full release cycle; only then sign with the new key
   alone. The app offers the newest release, not the next one, so a copy that trusts only the old
   key updates from the app only to a release the old key still signs: the longer the overlap,
   the fewer players left behind, and a copy older than the overlap's end must be updated by hand
   once.

**A lost key.** Losing the signing key while the cold backup is trusted: promote the backup
(step 1 above); no player notices. Losing both: make a new key, trust it in the next release,
and say in that release's notes that players install it by hand once; a copy that trusts only
lost keys refuses every later release ("This release can't be installed from here."), because
nothing can sign for those keys any more.

**What this protects against:** a file or checksum list changed on GitHub. Not against theft of
a private key: that is the same trust as any signing key held in a secret store.
